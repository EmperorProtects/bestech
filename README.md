# BESTECH — портал: кабинет заказчика и цифровой двойник

Рабочий прототип платформы BESTECH (ТОО «Бек Строй Инвест», Астана): аутентификация,
SQLite, загрузка файлов и выдача чертежей. Разделы стадий «Строительство» и
«Эксплуатация» видны в навигации, но помечены «в разработке» — см. «Стадии и флаги».

## Стек

- **Next.js 14 (App Router)** + React 18 + TypeScript (strict)
- **SQLite через `node:sqlite`** — встроенный модуль Node 22.5+, без внешних пакетов
  и нативной сборки; БД и загруженные файлы лежат в `apps/portal/.data`
- **Сессии на scrypt + httpOnly-cookie** — без сторонних библиотек аутентификации
- **Zustand** — клиентское состояние (тема, плотность, выбор датчика/отклонения, фильтры)
- **pnpm workspaces** — монорепо
- **lucide-react** — иконки, stroke-width 1.5

Ни одной внешней зависимости сверх того, что было в макете: БД, хеширование паролей,
ZIP-архив и генерация чертежей собраны на стандартной библиотеке Node.

## Запуск

```bash
pnpm install
pnpm dev          # http://localhost:3000 → /login
pnpm build
pnpm typecheck
pnpm lint
```

При первом обращении к БД создаётся `apps/portal/.data/bestech.db` и засеивается
демо-данными (организация, три объекта, ведомость ПД, замечания нормоконтроля).
Чтобы начать с чистого листа — удалите каталог `.data`.

## Стадии и флаги

Единственный источник истины — `apps/portal/src/lib/stages.ts`. По умолчанию открыта только
стадия «Проектирование»; остальные включаются переменной в `apps/portal/.env.local`:

```bash
NEXT_PUBLIC_BESTECH_ENABLED_STAGES=design,construction
```

После изменения `.env.local` перезапустите `pnpm dev` — переменная `NEXT_PUBLIC_*`
встраивается и в клиентский код.

**Работает (стадия «Проектирование»):**

- B2 список объектов, B3 лист объекта
- B4 исходные данные — **загрузка файлов** на диск с записью в БД, пересчёт
  комплектности, запрос недостающих документов
- B5 ведомость разделов ПД, B6 просмотр листа с замечаниями нормоконтроля
- **получение чертежей** — просмотр листа, скачивание листа, скачивание раздела
  и всего комплекта одним ZIP-архивом

**В разработке (стадии «Строительство» и «Эксплуатация»):** цифровой двойник,
телеметрия, сравнение «факт / проект», аварии, ход СМР, БПЛА и сканирование,
исполнительная документация, эксплуатация и обслуживание. Пункты меню и вкладки
остаются видимыми и неактивными, маршруты `/twin/*` отдают экран-заглушку с
объяснением, от чего зависит раздел. Разметка и компоненты этих разделов написаны —
чтобы их включить, достаточно добавить стадию в `ENABLED_STAGES`.

Сквозные функции вне объёма (финансы, команда, ИИ-сервисы) закрыты тем же
механизмом через `disabled: true`.

## Цифровой двойник: приём данных с датчиков (демо-стенд)

Стадия «Строительство» открывается флагом (см. выше). На объекте `2026-014` зарегистрировано
12 датчиков: температура и прочность бетона, осадки марок, нагрузки на фермы, трещиномер,
давление ВК, загрузка трансформатора (`src/lib/twin/catalog.ts` → таблица `sensors`).

**API приёма** — то, во что шлюз стройплощадки (LoRaWAN / MQTT / Modbus → HTTP) превращает
поток датчиков. Сессия не нужна: устройство предъявляет свой ключ.

```http
POST /api/ingest/v1/readings
Authorization: Bearer <ключ устройства>
Content-Type: application/json

{ "device": "gw-01", "readings": [ { "sensor": "Ф-2", "value": 72.4, "ts": "2026-09-14T10:00:00Z" } ] }
```

- `202` — принято (в ответе `accepted`, `rejected` с причинами и открытые тревоги), `422` — ни одного
  годного показания, `400` — не JSON, `401` — неверный ключ. Каждый пакет пишется в журнал.
- `GET /api/ingest/v1/health` — проверка связи, `GET /api/ingest/v1/sensors` — конфигурация для шлюза.
- Порог допуска открывает аварию (предупреждение → авария), возврат в допуск закрывает;
  датчик, молчащий дольше 4 периодов опроса, получает аварию «нет связи». Каждая авария попадает
  в ленту объекта в кабинете заказчика.

**Экраны двойника** обновляются каждые 2 секунды: обзор модели с датчиками, телеметрия
(окна 5 мин / 15 мин / 1 ч), **аварии** (квитирование, закрытие, динамика параметра),
**приём данных** (журнал входящих пакетов, точка приёма, примеры curl и PowerShell).

**Эмулятор датчиков** — отдельный процесс-шлюз `apps/portal/scripts/sensor-simulator.mjs`,
шлёт показания через тот же API. Запуск:

- из портала: «Двойник → Приём данных → Запустить эмулятор» (роль ГИП или технадзор);
- из терминала: `pnpm demo:sensors` (клавиши `1` перегруз Ф-2, `2` осадка ГМ-07,
  `3` перегрев бетона, `4` обрыв связи ТП-1, `0` норма, `q` выход).

Ключ демо-шлюза — `bst_demo_2026-014_gateway` (`BESTECH_DEMO_INGEST_KEY`). Кнопка
«Сбросить демо-данные» удаляет показания, пакеты и аварии объекта перед показом.
На экране приёма эмулятор честно виден устройством `emulator-01`.

### 3D-модель двойника

На «Обзоре двойника» модель корпуса построена на three.js (`components/twin/ModelViewer3D.tsx`):
каркас 36 × 18 м линиями в стилистике чертежа, фермы, кровля, оси; датчики стоят по привязке
(`lib/twin/model3d.ts`). Цвет метки — состояние датчика, при выходе за допуск метка пульсирует,
ферма с перегрузом окрашивается. Мышью: ЛКМ — вращать, колесо — масштаб, ПКМ — сдвиг; клик по
датчику выбирает его, камера подлетает. Кнопки видов: изометрия, сверху, фасад, автовращение.
Переключатель «3D МОДЕЛЬ / СХЕМА» возвращает прежнюю SVG-схему; без WebGL схема включается сама.

### Пульт показаний для заказчика (`apps/sensor-console`)

Отдельный сайт без зависимостей: заказчик двигает ползунки или вводит значения датчиков, и
через 1–2 секунды они отражаются на 3D-модели, в телеметрии и в авариях портала.

```bash
pnpm console          # http://localhost:4000 и адреса в локальной сети — открывается с телефона
```

- Сервер пульта пересылает значения в портал через `POST /api/ingest/v1/readings`; ключ устройства
  хранится только на сервере пульта. Устройство в журнале пакетов — `customer-console`.
- Сценарии в один клик: перегруз фермы, осадка, перегрев и мороз бетона, трещина, «всё в норме».
- «Держать связь» повторяет все значения каждые 5 с, иначе датчики без эмулятора уйдут в «нет связи».
- Ручной ввод 2 минуты имеет приоритет над эмулятором: его показания по этим датчикам отклоняются.
- Настройка: `PORTAL_URL` (по умолчанию `http://127.0.0.1:3000`), `DEVICE_KEY`, `DEVICE_ID`,
  `PORT` (4000), `HOST`, `CONSOLE_PIN` — PIN для доступа, если пульт открыт в общей сети.

## Мастерская выпуска чертежей (newExport)

Портал связан с рабочим окружением `Documents\newExport`, где Claude Code выпускает
чертежи в Revit через RevitBridge и скиллы (`revit-verify`, `normcheck`, `normcheck-ar`,
`smeta`). Мастерская — источник истины для проектной выдачи: портал ничего не копирует,
а читает её папки по соглашению (`apps/portal/src/lib/workspace.ts`).

| В мастерской | В портале |
| --- | --- |
| файл с шифром `NNN-ГГГГ-МАРКА` в `01_Исходные данные`, `05_Модели`, `04_Чертежи` | объект стадии «Проектирование» |
| `01_Исходные данные\ТЗ_<шифр>.md` (поля `Объект`, `Стадия`, `Место строительства`) | карточка объекта, строка «ЗАД» в исходных данных |
| `04_Чертежи\<шифр>_альбом.pdf` | раздел документации; лист = страница PDF, просмотр со своей страницы |
| `04_Чертежи\<шифр>_альбом.json` | номера и названия листов (без него — «Лист 1…N») |
| `03_РПЗ\<шифр>_РПЗ.md` | раздел «ПЗ» |
| `05_Модели\<шифр>.rvt` | размер и дата модели на вкладке «Мастерская» |

Обратное направление:

- **Загрузка исходных данных** в кабинете по связанному объекту кладёт копию файла в
  `01_Исходные данные` с префиксом шифра — Claude видит её в следующем задании.
- **Вкладка «Мастерская»** — статус сервера Claude (`_web`) и Revit (по `bridge.lock`),
  запуск заданий: выпуск альбома, нормоконтроль планировки и листов, проверка листов,
  РПЗ, смета, своя задача. Журнал выполнения идёт вживую, после завершения выдача
  пересинхронизируется и в ленте объекта появляется событие.
- Задания отправляются в существующую обёртку `newExport\_web\server.py` (запуск —
  `_web\start.bat`), которая держит права `--permission-mode`, хуки и MCP. Токен обёртки
  читается сервером портала и в браузер не попадает. Запускать и останавливать задания
  может только роль «проектировщик» (ГИП); заказчик видит статус, историю и итоги.
- Одновременно идёт одно задание — RevitBridge обслуживает один документ.

### Новый проект по ТЗ

ГИП создаёт проект кнопкой «Новый проект по ТЗ» в «Моих объектах» (`/cabinet/assets/new`):
шифр (следующий свободный номер подставляется), марка, стадия, объект, место, заказчик,
текст задания и/или файл ТЗ. Портал пишет `01_Исходные данные\ТЗ_<шифр>.md` в мастерскую,
объект сразу появляется в кабинете, по галочке стартует задание **«Проект по ТЗ»**.

Задание ведёт проект по этапам регламента: модель из шаблона АР → геометрия → проёмы →
помещения → normcheck-ar → оформление → листы → альбом и РПЗ. Claude отмечает этапы в
`05_Модели\<шифр>_этапы.json`; вкладка «Мастерская» показывает ход, а кнопка
«Продолжить проект» запускает следующее задание с первого незакрытого этапа. Шаблон —
`BESTECH_AR_TEMPLATE`, по умолчанию ADSK_RU r2021 v2.2.3 из `newExport\CLAUDE.md`.

Синхронизация идёт при открытии страниц кабинета, не чаще раза в 10 секунд, и сразу
после каждого задания. Соглашение о выдаче продублировано в `newExport\CLAUDE.md`.

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `BESTECH_WORKSPACE_DIR` | папка мастерской | `~\Documents\newExport` |
| `BESTECH_WORKSPACE_ORG` | организация, в которую попадают проекты мастерской | первая организация |
| `BESTECH_CLAUDE_WEB_URL` | адрес обёртки Claude мастерской | `http://127.0.0.1:8090` |
| `BESTECH_CLAUDE_WEB_TOKEN` | токен обёртки | читается из `_web\.token` |
| `BESTECH_REVIT_BRIDGE_DIR` | папка RevitBridge | `~\Documents\RevitBridge` |

## Аутентификация и доступ

- Пароли — scrypt (`node:crypto`), формат хеша `scrypt$N$r$p$salt$hash`.
- Сессия — случайный токен в httpOnly-cookie `bestech.sid`, в БД хранится только
  его SHA-256; срок 14 суток, протухшие чистятся при каждом входе.
- `middleware.ts` работает в Edge-рантайме и проверяет только наличие cookie;
  настоящая проверка — `requireUser()` в серверных компонентах и обработчиках,
  поэтому подделанная cookie ничего не даёт.
- Все выборки по объектам ограничены организацией пользователя: чужой шифр в
  адресе отдаёт 404, а не чужие данные.

## Чертежи

Лист отдаётся в таком порядке: загруженный проектировщиком исходник (PDF/DWG),
иначе — лист, собранный из данных БД в `lib/sheet.ts`: рамка и основная надпись
по ГОСТ 2.104 (форма 1), сетка осей с марками, размерные цепочки с засечками,
отметки уровней. Вид поля зависит от наименования листа: план, разрез, фасад
или ведомость. Комплект собирается в ZIP (`lib/zip.ts`, метод store) — по папке
на раздел плюс `Ведомость чертежей.txt`.

## Подключение внешнего бекенда

Менять нужно только `apps/portal/src/api/index.ts`: заменить SQL-запросы на
`fetch`. Соответствие функций и эндпоинтов описано в шапке файла, типы в
`api/types.ts` — контракт между фронтом и бекендом.

## Темы и плотность

`data-theme` и `data-density` ставятся на `<html>` компонентом `ThemeController`.
По умолчанию раздел задаёт тему: кабинет — «Бумага», двойник — «Цианотипия»
(операторская). Пользовательский выбор в сайдбаре перебивает раздел и сохраняется
в `localStorage` (`bestech.ui`).

## Соглашения по UI

- Цвет никогда не единственный сигнал: состояние — это цвет + глиф (`●` `▲` `✕`) + подпись.
  Используйте `ToleranceStamp` / `StatusStamp`, а не собственные бейджи.
- Рамка объекта — `<Frame>`: тонкая линия и четыре угловые засечки; засечки не опускаем.
  Угловые засечки у кнопок — только у главной (`ticks`).
- Значения, шифры и координаты — моноширинным с табличными цифрами (`.bst-mono`).
- Графики и модель — только линии: пороги пунктиром, никакого фотореализма.
- Даты `ДД.ММ.ГГГГ`, тысячи через пробел, валюта `₸` — через `lib/format.ts`.
- Закрытый раздел подписывается одним текстом — `IN_DEVELOPMENT_LABEL` из `lib/stages.ts`.

## Деплой демо-стенда на Render

`render.yaml` в корне описывает один web-сервис с постоянным диском: кабинет, документация
и двойник. Мастерская в облако не едет — Revit и сервер Claude живут на рабочей машине,
поэтому в сервисе `BESTECH_WORKSPACE_DIR` указывает на пустой путь и вкладка мастерской
показывает «объект не связан».

1. Залить репозиторий на GitHub (Render деплоит из Git).
2. Render → New → Blueprint → выбрать репозиторий: сервис, диск и переменные создадутся сами.
3. Заполнить переменные без значения: `BESTECH_DEMO_PASSWORD` и `BESTECH_DEMO_INGEST_KEY`.
   Пароль задать **до** первого запуска: он пишется в базу при засеве.
4. После первого деплоя вписать выданный адрес (например `bestech-portal.onrender.com`)
   в `BESTECH_PUBLIC_HOST` и сделать Manual Deploy — без него Next отклоняет вход и
   загрузку файлов как межсайтовые запросы.

| Переменная сервиса | Значение |
| --- | --- |
| `NODE_VERSION` | `24` — `node:sqlite` есть только с Node 22.5+ |
| `BESTECH_DATA_DIR` | `/var/data` — база и файлы на постоянном диске, переживают деплой |
| `NEXT_PUBLIC_BESTECH_LIVE_POLL_MS` | `15000` — в облаке опрос реже, чем на локальном показе |
| `PORT` | подставляет Render; `next start` читает её сам |

Пульт показаний и эмулятор остаются локальными процессами и работают с облаком через
адрес портала:

```powershell
$env:PORTAL_URL = 'https://bestech-portal.onrender.com'; $env:DEVICE_KEY = '<ключ шлюза>'; pnpm console
node apps\portal\scripts\sensor-simulator.mjs --url https://bestech-portal.onrender.com --key <ключ шлюза>
```

Ограничения: диск работает с одним экземпляром сервиса (автомасштабирование не включать),
бесплатный тариф Render засыпает через 15 минут и не поддерживает диск — для доступа
на недели нужен Starter.

## Демо через ngrok

Показ портала заказчику по временной ссылке, без деплоя:

```powershell
.\scripts\demo-ngrok.ps1            # туннель + портал, опрос экранов 6 с
.\scripts\demo-ngrok.ps1 -Console   # ещё и пульт показаний на localhost:4000
.\scripts\demo-ngrok.ps1 -Stop      # остановить всё
```

Скрипт поднимает ngrok на порт 3000, забирает публичный адрес из API ngrok и только потом
запускает портал, передав ему адрес в `BESTECH_PUBLIC_HOST`. Без этой переменной Next
отклоняет server actions (вход, загрузка файлов) как межсайтовые запросы.

Что нужно знать перед показом:

- **Заглушка ngrok.** Первому посетителю показывается страница «Visit Site». Откройте ссылку
  сами до звонка, тогда заказчик её не увидит (cookie живёт 7 дней).
- **Опрос экранов.** По умолчанию скрипт ставит `NEXT_PUBLIC_BESTECH_LIVE_POLL_MS=6000`: на
  бесплатном ngrok лимит 20 000 запросов в месяц, а при штатных 2 с одна вкладка тратит
  около 1 800 запросов в час. Скрытая вкладка портал не опрашивает.
- **Пульт и эмулятор остаются локальными** и обращаются к порталу на `127.0.0.1:3000` —
  выводить их в туннель не нужно.
- **Мастерская работает и через туннель**: её код выполняется на сервере портала, то есть на
  этой машине, и обращается к папкам `newExport` и к `_web` на `127.0.0.1:8090` со стороны
  сервера. Нужны запущенные `_web` и Revit с мостом. Но заходить клиенту давайте под
  учётной записью заказчика: роль ГИП позволяет запускать задания и писать файлы на вашем
  компьютере.
- Демо-учётки и ключ шлюза — демонстрационные. Прежде чем давать ссылку наружу надолго,
  поменяйте пароли и ключ.
